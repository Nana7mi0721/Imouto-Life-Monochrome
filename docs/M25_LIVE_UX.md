## 1. §一 RNG：opt-in 游标扰动

### 1.1 前提核实

`crates/wolf-vm/src/rng.rs` 的游标是**数据定义**的：`Game.dat` 里那张 7-bit 静态
随机表由一个游标顺序读出，`from_game()` 固定从 0 起，所以"新开局"和"反复读同一个档"
抽到的序列完全一样——这是零售行为，本仓的视觉基线与商店/夜事件期望值都钉死了这条抽取顺序。

所以"每次不同"是**产品决定**，不是保真修复，必须挂在开关后面。

### 1.2 落地

* `crates/wolf-vm/src/rng.rs` 新增
  * `LIVE_RNG_ENV = "WOLF_LIVE_RNG"`、`live_rng_enabled()`、`live_jitter()`；
  * 可注入 API `from_game_with_live` / `from_game_with_cursor` / `set_cursor_live` /
    `set_cursor_with_live` / `set_cursor_with_jitter`。
  * `live_jitter()` = 纳秒 × `0x9E3779B97F4A7C15` 旋转 23 位 ⊕ 原子计数器 ×
    `0xBF58476D1CE4E5B9`，再折一次高位，保证同一秒内两次请求也不同。
* `crates/wolf-game/src/savegame.rs:168`：读档入口改用 `set_cursor_live`（原来用
  `set_cursor(playtime_frames)`）。**playtime 定位保留**，live 只是再平移。
* **默认路径逐位等价**：环境变量没设时，`from_game()` 与 `set_cursor_live()` 的结果与
  改动前完全相同——回归基线不受影响。

### 1.3 用法与坑

* 开：`WOLF_LIVE_RNG=1` 启动 Godot（或 CLI）。关：不要设这个变量。
* **它是进程级环境变量**：全局导出它会连零售对照测试（种子夹具、视觉基线）一起带偏，
  跑回归前要撤掉。
* 回归测试**不碰环境变量**（Rust 的 `set_var` 与并行测试有 data race），走可注入 API。
* 回归：`crates/wolf-game/tests/m25_live_rng.rs` **15 条**。

## 2. §二 光标：**核实结论是引擎没坏**

方案 §二 的前提（"非恶作剧界面的跟随鼠标手指图标没做出来，所以要修引擎"）经核实
**不成立**。零售的手型指针就是 **Picture 2999**，而 2999 **本来就是通的**。

### 2.1 零售是怎么做的（实测，不是推测）

| 事实 | 证据 |
| :--- | :--- |
| 指针图 = Picture 2999 | `SampleMapA.mps` **Ev 14「マウス追従」**（parallel，条件 `var120 == 1`）画 `150 [4096, 2999, 0, 6, 4, 1, 255, 1100000, 1100001, 100, 0] "CharaChip/hand3.png"` |
| 坐标来自 Sys71/72 | `124 [1100000, 4096, -2, 6]` / `[1100001, 4096, -2, 7]` 写入 `1100000/1100001`，再被 Ev 14 读出 |
| 图是一张 **6×4** 帧表 | `CharaChip/hand3.png` = 192×128 = 每格 32×32（`ux方案.md` 写的 4×1 / 48×128 **是错的**） |
| 零售画面里确实有它 | `ptr_sc/卧室_点击妹妹_首句话.png` 模板匹配命中 hand3 帧 0 @ 游戏坐标 (320, 356)，得分 2054 |

### 2.2 为什么玩家看不到它

`var120` **只在夜间流程之后才为 1**：

* `CE 230`（深夜1）pc46 `var120 = 1` + pc47 `var100 = 1`；
* `CE 227`（深夜1表示）pc50 `var120 = 0`；
* 调用 `CE230` 的是 ev12（就寝妹）与 ev23（深夜表情自動変更）。

**零售 5 个存档实测**（用本仓引擎读零售存档）：

| 存档 | 进度 | `var120` |
| :--- | :--- | :--- |
| retail-01/02/03/04 | 白天 | `0` |
| retail-05 | 第 4 天 23:00（夜里） | `1` |
| 本仓端口存档 | 第 1 天 19:00 | `0` |

结论：**零售也是"妹妹上过床之后"才有手型光标**。玩家的存档停在第 1 天 19:00，
所以没有——**与零售一致**，不是 bug。

### 2.3 处置

* **保持零售行为**（本轮不为此改引擎一行）。
* 方案里的"Godot 侧挂一个硬件自定义光标"**已否决**：会与 2999 的手型光标闪烁冲突，
  也偏离零售。
* 若产品上确实要"日常界面也常驻手型光标"，那是**偏离零售**的决定，需要另开一个
  显式开关并单独立项。
* 回归：`crates/wolf-game/tests/m25_cursor_follow.rs` **4 条**（`var120 = 1` 时 2999
  画 hand3.png / split(6,4) / cell 1 / anchor 1 / 32×32 居中于指针；`var120 = 0` 时
  没有；跟随移动；`CE230` 打开开关）。

### 2.4 一条文档订正

`2000110` 是**普通变量 110**，不是引擎 Sys110（Sys 变量在 `9_000_000 + n` 命名空间，
`SYS_BASE = 9_000_000`）。`rng.rs` 的模块文档原本是对的，订正的是引用它的报告。

## 3. §三 睡姿妹妹的热区

### 3.1 报告的因果是错的

> 报告："pose 5 没有 CE240 的 900..903 槽位"

实测：**CE240 随时可以画这四个槽位**，与 `v14` 无关（白天的并行页 ev30 独立调用
CE240）。真正的根因是宿主侧 `game.rs:3402` 的**无条件早退**：
`pose == 5` 直接 `return`，于是 alpha 轮廓判定根本没机会跑。

### 3.2 落地

`crates/wolf-game/src/game.rs` `sister_body_action_event_at()`：

1. 删掉 `pose == 5` 早退；
2. 判定顺序改成 **轮廓命中优先 → 地图矩形兜底**（兜底仍然只给 `pose == 5`，
   矩形 `144,320,144,64` 原样保留）；
3. 顺手修掉一个自己写出来的缺陷：`action_key_rect(...)` 原先排在轮廓判定之前，
   地图里没有 ev12 时会提前返回 `None`。

### 3.3 两处**没有**照方案做的事（及原因）

| 方案 | 为什么不做 |
| :--- | :--- |
| 把 ev12 兜底矩形"向下/向右扩到 120×96" | 方向错了：缺口在**上方**（头部 y 248..304），而且 `width.max(120)` 对 144 是恒等。方案自己要求先用夜间卧室实机截图核对床铺上妹妹的像素坐标，本轮没有该截图，按 `AGENTS.md` 不臆造 UI 数值 |
| 把 `item_icon00..03`（1112..1115）加进 `PICTURE_ACTION_CONTROLS` | 会**破坏 ev26 的 op124 点击链**（那四个图是 ev26 的事件图标，不是妹妹的立绘） |

### 3.4 回归

`crates/wolf-game/tests/m25_sister_pose5.rs` **4 条**，其中"睡姿点立绘中心 → `Some(12)`"
这条内含"点击点必然在 ev12 矩形之外、且 ev1/2/3/4/25 无地图矩形"的断言，
**旧代码必然失败**，确实卡住了这个修复。

> 坑：`Game::last_action_event` 只在 `reset_to_title` 清空，所以负例必须用**全新 game**，
> 否则会被上一条用例的残留状态骗过去。

## 4. §四 存读档：返回标题入口 + 存单弹窗 + 槽 1 自动存档

### 4.1 先解决的两个"入队安全"问题

方案里写的两处**编不过 / 调不到**，本轮改成了能编译、能调用的形式：

| 方案原文 | 问题 | 本轮做法 |
| :--- | :--- | :--- |
| `Game::save_requests` 直接 push | 该字段是 **private**，两份文档都漏了，**没有任何公开 API 能入队 `SaveRequest::Load`** | 新增公开方法 `Game::request_load(&Path)`，内部 push 到 `save_requests`，由 `Game::frame` 在 VM step 之后统一结算 |
| `Path::new(path.to_string().as_str())` | **E0716**，编译不过（临时值被借走） | gdext 侧 `let path = std::path::PathBuf::from(path.to_string());` |

`request_load` 走的是和游戏自己的 `220` opcode **完全同一条路**：
`load_into` → `flush_pending_sounds` → `boot_map_active = false` →
`retire_load_ui_chain`（收掉 CE14/CE131 这条菜单链）→ `resume_loaded_map`（把存档里的
地图装回来）。所以"游戏内便利读档"不会留下一个挂着菜单的半截会话。

### 4.2 存单弹窗：单击即覆盖是真问题

零售 CE131 存档格**左键点一下就直接覆盖该槽**（没有确认框），误点 = 毁档。
本轮在 **Godot `_input` 的最顶部**拦截（`_handle_mouse_button` 之前），
命中**非空**槽时：

* 吞掉这次点击（`mouse_down` / `mouse_latch` 清零，运行时这一帧看不到点击）；
* 弹出自绘面板（`_ModalLayer`），三个按钮：
  * **保存到此槽** → **把原点击重放给运行时**（`_pending_click`），让游戏自己写槽。
    这样 `System.sav` 的"上次写的是第几槽"也由游戏自己更新，前端写文件做不到这件事。
  * **读取此存档** → `wolf.request_load(path)`，走 §4.1 的安全入队路径。
  * **取消** → 什么都不做。
* 空槽**不弹窗**：游戏照常写入（没有东西可毁）。
* 标题界面的读档格是"读"模式，弹窗只有 **读取此存档 / 取消** 两个按钮。

### 4.3 CE131 的槽号算法（实测钉死）

方案里的 `page * per_page + idx + 1` 只是猜的。实测把 CE131 的 self 变量全部读出来后：

| self | 含义 | 实测值 |
| :--- | :--- | :--- |
| `600` | 模式：**0 = 写**（游戏内存档格）、**1 = 读**（标题读档格） | 游戏内 `0`，标题 `1` |
| `610` | 页内行号（0-based） | 宿主 `sync_save_grid_cursor` 写的就是它 |
| `611` | 页号（0-based） | `0 / 1 / 2` |
| `612` | 光标的**绝对槽号** | `1 / 5 / 9` |
| `613` | 总页数 | `3` |
| `626` / `627` | 每页行数 / 每页槽数 | `4 / 4` |

**绝对槽号 = `611 * 627 + 610 + 1`**，共 **12 槽 / 3 页**。
实测写盘验证（点第三行面板）：

| 页 | 绝对槽号 | 实际写出的文件 |
| :--- | :--- | :--- |
| 第 1 页 | 3 | `SaveData03.sav` |
| 第 2 页 | 7 | `SaveData07.sav` |
| 第 3 页 | 11 | `SaveData11.sav` |

槽位面板就是 `12050 + 20 * 行` 这几张图，命中盒用 `Screen::picture_rect` 的**面板盒**
（928×115），不是 18×18 的皮肤贴图。

### 4.4 返回标题入口

* `crates/wolf-game/src/game.rs`：`Game::trigger_return_to_title()` —— 复用脚本
  `174 ReturnToTitle` 的同一个标志位，**帧末**才拆地图，不会在帧中砸坏调度器。
* `crates/wolf-gdext/src/lib.rs`：`return_to_title()` / `at_title()`。
* `godot/scripts/GameView.gd`：`Esc` 打开自绘确认面板（**是 / 否**，默认焦点在"否"）。
  浮层期间键盘、滚轮、鼠标全部吞掉，左键只在按钮矩形内生效。

> **Esc 语义变更（需要知悉）**：`Esc` 现在是前端专用键，不再是运行时的取消别名。
> 说明书里取消键是 Backspace / X / 右键，这三个仍然可用。

### 4.5 晚饭后槽 1 自动存档

* 触发点：`CE 258`（晩ごはん処理）**正常结束**的那一帧（`ce258_running` 边沿检测）。
  结束时写 `Save/SaveData01.sav`，并给前端一个 120 帧的横幅。
* **宿主开关**：`Game::set_auto_save_slot(Option<u32>)`。**默认关**。
  * 回归套件默认不写任何存档，所以 `work/Data/Save/` 不会被测试跑花。
  * Godot 前端只在**真窗口 + 非 capture** 的会话里打开（`DisplayServer` 非 headless、
    没有 `--capture=`、没有 `--auto-new-game`）。
* 不会保存的情况：还在标题（`boot_map_active`）或正要回标题（`pending_return_to_title`）。

> **注意**：槽 1 是玩家的正常存档槽。开着自动存档玩到晚饭后，**槽 1 会被覆盖**。
> 这是 `ux方案.md` 写明的需求（"槽 1 自动存档"），本轮照做；如果想改成独立的自动存档槽，
> 只需要改 `Game::set_auto_save_slot` 的那个槽号。

## 6. 坑

1. **`Game::save_requests` 是 private**：两份文档都以为能直接 push，实际没有公开 API。
2. **`Screen::picture_rect` 对窗口图给的是面板盒**（928×115），不是 18×18 皮肤——
   命中盒写错就会"点了第一格"。
3. **CE131 的 12 个槽跨 3 页**：只看行号会把第 2 页的第三行当成槽 3。
4. **标题读档格与游戏内存档格是两种模式**（self600 = 1 / 0）：弹窗按钮表要跟着变。
5. **`Game::assets::texture_size` 要 `&mut`**，所以 `save_slot_at` 只能是 `&mut self`。
6. **gdext 的 `Dictionary::set` 对 `GString` 要传引用**（`&path`），否则 E0271。
7. **Godot 的按键必须跨物理帧**：按下与抬起放在同一帧里，`held_keys` 还没被
   `_physics_process` 读到，按键等于没按。测试里的 `_press` 因此要 `await physics_frame`。
8. **自动存档是破坏性的**：槽 1 是玩家槽位；回归套件默认关闭，Godot 只在真窗口会话打开。
