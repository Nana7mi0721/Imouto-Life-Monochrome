## 二、9 项实机问题逐项根因分析与修复方案

### 1. 点击对话右下角闪现巨大妹妹头像

- **问题现象**：推进对话或点击关闭对话框瞬间，画面右下角会短暂闪现一个较大的妹妹头像（原版原生对话框体系的立绘/头像）。
- **代码定位**：
  - `crates/wolf-game/src/game.rs:170`：`NATIVE_MESSAGE_PICTURES = &[19_500, 19_501, 19_502, 19_503]`
  - `crates/wolf-game/src/game.rs:1808-1816`：在 `picture_quads()` 中仅当 `balloon_owns_message` 为 `true` 时，才执行 `quads.retain(|quad| !(19_500..=19_503).contains(&quad.number))` 过滤掉 `19502`。
  - `crates/wolf-game/src/game.rs:2232-2256`：`balloon_owns_message()` 依赖 `self.balloon_visuals_active()`，而后者仅在 `!self.messages.is_empty()` 或 `36000..=36014` 仍可见（`!hidden && opacity > 0`）时返回 `true`。
- **根因分析**：`19500..=19503` 作为原生 `101` 对话系统槽位一直驻留在 `self.screen` 中。当玩家点击结束对话、`messages` 清空且气泡槽位 `36000..=36014` 刚隐藏或淡出至 `opacity == 0` 的那一帧，`balloon_visuals_active()` 立即变为 `false`，导致 `balloon_owns_message()` 返回 `false`，原本被屏蔽但**从未被真正擦除**的 `19502` 大头像就会立刻漏出渲染。
- **修复建议**：当对话以气泡模式（`balloon_picture_mode_enabled()`）推进结束并清空 `messages` 时，同步擦除或隐藏 `19500..=19503` 槽位（或在 `balloon_picture_mode_enabled()` 为 `true` 时始终排除 `19500..=19503` 参与渲染，仅保留其逻辑输入状态）。

### 2. 妹妹对话框过高导致头像顶部留空

- **问题现象**：对比零售截图（`{DC101038-B86D-49B3-B098-EC86FC084894}.png`）与当前运行截图（`{1C862961-0D6D-4A79-81B2-D381BF0A5E23}.png`），当前妹妹对话框顶部显著偏高，导致妹妹头顶呆毛上方出现一大块灰黑色空余区域；零售版中对话框上沿更低，妹妹呆毛顶端几乎贴近对话框上沿及「妹妹」名牌下方。
- **代码定位**：
  - `crates/wolf-game/src/game.rs:175-179`：`BALLOON_FACE_FRAME_MIN_HEIGHT: i32 = 136`
  - `crates/wolf-game/src/game.rs:295-305`：`BALLOON_FACE_BOTTOM_Y: f32 = 563.0`
  - `crates/wolf-game/src/game.rs:1797-1806, 2326-2348`：`balloon_frame_render_rect()` 与 `quad.number == BALLOON_FACE_PICTURE` 锚定逻辑。
- **根因分析**：为了给头像留出空间，代码将含头像时的气泡最小高度硬编码抬高到了 `136 px`（而单行基础高度 `BALLOON_FRAME_MIN_HEIGHT` 为 `60 px`）。由于气泡框向顶部生长（`rect[1] -= growth`），`136 px` 的高度比零售版高出约 `18~22 px`，且同时把上方的名牌 `36008..=36012` 一并向上推高，造成头像上方出现明显空缺。
- **修复建议**：对照零售截图像素高度将 `BALLOON_FACE_FRAME_MIN_HEIGHT` 从 `136` 下调至 `114~118` 左右（使气泡上沿位于 `y ≈ 446~450`，与头像顶部 `y ≈ 444` 形成轻微探出/贴合的视觉关系），并同步微调 `BALLOON_FACE_BOTTOM_Y` 验证真机对齐效果。

- **字节码与代码定位**：
  - `CE 277`（`┣警戒度メータ`）：使用 `Picture 500` 绘制底框（`\img[Picture\box01.png]`）、`Picture 501` 绘制填充格（`\img[Picture\box02.png]`）、`Picture 502` 绘制文字「警戒度」。
  - `CE 281`（`カットインタイマー右`）与 `CE 282`（`カットインタイマー左`）：同样循环绘制 `500..=502` 格子条。
  - `CE 249`（`┣お風呂`）正常/被发现分支：`pc=202`、`pc=464`、`pc=565`、`pc=643`、`pc=838` 等处均带有 `150 Erase [16777218, 500, 0, 0, 0, 502/521]`。
- **根因分析**：`CE 249` 在正常分支末尾会擦除 `500..=502`，但当偷窥过程触发高潮/被发现打断、进入 `ゲーム结束判定` 或并行/定时子事件（`CE 281/282` 或 `CE 275`）仍在后台/残留协程队列中执行时：
  1. 若并行事件在 `CE 249` 擦除 `500..=502` 之后又跑了一拍，会重新把 `500/501` 写回 `self.screen`；
  2. 或者部分打断分支在跳出 `CE 249` 时未经过 `500..=502` 的统一擦除节点（例如 `pc=565`/`pc=838` 仅覆盖了部分子分支，某些中断路径直接跳转到结局或地图切换）。
- **修复建议**：
  1. 在 `CE 249` 所有进入 `ゲーム结束判定` 或切回卧室地图的出口统一检查并补全 `500..=502` 擦除；
  2. 排查宿主/VM 在事件被中断或场景切回日常卧室时，是否未终止仍在运行 `CE 281/282` 等计时器子事件的协程实例，导致其在擦除后再次重绘 `500/501`。

### 4. 恶作剧界面鼠标移至两侧操作区时图标未变回手指

- **问题现象**：在夜袭/恶作剧界面中，鼠标先移动到妹妹身体各部位（图标变为 `look.png` 眼睛等，见 `{583A69F6-C59B-42CD-81A0-8EAFCB557940}.png`），再移动鼠标到左侧「触摸 / 衣服」或右侧「结束」操作按钮上时，光标仍保持在妹妹身上的最后图标，没有变回手指形态（`hand1.png`，参考 `{7CFA3EA2-F8A6-4ED8-A14E-EE17C1BC0CF0}.png`）。
- **字节码与代码定位**：
  - `SampleMapA.mps Ev 14`（光标绘制事件）：根据变量 `var 121`（`2000121`）刷新 `Picture 2999` 跟随鼠标坐标（`124 target=-2`）：`0 -> hand3.png`、`1 -> look.png`、`2 -> hand1.png`、`3 -> talk.png`、`4 -> hand2.png`、`5 -> mushroom.png`。
  - `SampleMapA.mps Ev 18`（`カーソル切り替え`）：在 `pc=0..38` 依次用 `124`（`1100000, 16384, <pic_id>, 8`）检测鼠标是否悬停在妹妹身体部位图片 `1100..=1108` 上，并在命中分支中写入 `var 121`（`0/1/2/3`）。
- **根因分析**：在 `SampleMapA Ev 18` 的当前逻辑中，各个分支仅在**命中**身体热区（`1100..=1108` 或 `1111`）时才改写 `var 121`；当鼠标离开身体热区并移动到两侧操作区按钮时，由于没有任何热区命中分支或默认重置分支把 `var 121` 写回 `2`（`hand1.png`），`var 121` 就会一直保持上一次悬停妹妹部位时的值，`Picture 2999` 也就不会切回手指图标。

### 5. BAD/GOOD 条粗细不一致与睡眠圆形图标无呼吸动效

- **问题现象**：底部/顶部状态槽中的 BAD 条与 GOOD 条粗细明显不一致，且中间显示睡眠状态的圆形图标（`Picture 2000` `Picture/sleeping_staus.png`）静止不动，缺少原版的周期性呼吸缩放动效（见 `{1F17C41F-3E53-498D-B0B7-4B70A6DC5420}.png`）。
- **字节码与代码定位**：
  - **BAD / GOOD 条粗细**：`CE 237` 中 `pc=21` 绘制 `1998`（BAD 外框）的参数为 `window=(217, 6), scale=-100`；`pc=26` 绘制 `1994`（GOOD 外框）的参数为 `window=(217, 8), scale=100`。数据本身分别给了 `6 px` 与 `8 px` 的高度，同时 `1998` 带有 `scale=-100` 水平镜像。
  - **睡眠图标呼吸效果**：`CE 237` 的运行模式为 `run = 2`（**并行处理 / 並列実行**，触发条件 `cond = 18`）。在 `CE 237` 中：`pc=35` 使用 `150 Show` 创建 `Picture 2000`（`sleeping_staus.png`），紧接着 `pc=41` 使用 `290`（`[112, 70, 2000, 2000, 5, 5, 180]`，即 `EFFECT_BREATH`）设置呼吸缩放。
  - `crates/wolf-game/src/picture.rs:1256-1267`：`PictureAction::Show` 每次执行都会新建 `Picture::new(cmd.number)` 并覆盖插入 `self.pictures`，其中 `breath` 被初始化为 `None`。
- **根因分析**：
  1. `CE 237` 作为 `run = 2` 的并行事件每帧循环执行时，`pc=35` 的 `150 Show` 每帧都会重新创建并覆盖 `Picture 2000`，将上一帧已经累积了 `elapsed` 的 `picture.breath` 直接清零；紧接着 `pc=41` 虽然重新挂上 `Breath::new(..., elapsed: 0)`，但每一帧 `elapsed` 都停留在 `0`（`phase = 0 -> growth = (0, 0)`），导致图标永远处于静止原始大小。
  2. BAD 与 GOOD 外框在 `CE 237` 原始数据中高度分别为 `6` 与 `8`，加上 `WindowFile` 9-slice 边框渲染在极小高度（`6 px` vs `8 px`）下的像素取整差异，视觉上进一步放大了粗细落差。
- **修复建议**：
  1. 对同图同参数的 `150 Show`（或按原版引擎语义），若目标槽位已存在且核心图像/位置未变，或仅在状态值变化时重绘，避免每帧清空 `breath` / `zoom` / `pattern` 等 `290` 持续性特效的 `elapsed` 状态（或检查 `CE 237` 为何每帧重复进入该分支）；
  2. 核对零售版 BAD/GOOD 框在 `WindowBase` 9-slice 下的实际渲染高度，确认是统一以 `8 px` 渲染还是保留像素取整差异。

### 6. 仍有残留对话文字乱码（`哦。ュク邵遑ュ」ソ`）

- **问题现象**：部分含「哦」「…」「？」的中文对白仍显示为半角片假名混杂的乱码（如 `{0CF632BB-561D-4A34-A909-242F61EA4BB5}.png` 中的 `哦。ュク邵遑ュ」ソ`）。
- **字节码与代码定位**：
  - 字节码实测：`SampleMapA.mps Ev 17 pc=388` 解码为 `\\E哦｡ｭ｣ｿｸ遑ｭｸ遑ｭ｣ｿﾎﾒ｡ｭﾎｪﾊｲﾃｴ｡ｭ｣ｿ`，`CE 295 pc=53` 解码为 `\\E哦｡ｭｸ遑｢ｸ邵遑ｭ｣｡｣ｿ`。
  - 编码验证：中文原文 `哦…？哥哥…？` 的 GBK 字节为 `c5 b6 a1 ad a3 bf b8 e7 b8 e7 a1 ad a3 bf`；若按 CP932 解码，恰好变成 `ﾅｶ｡ｭ｣ｿｸ邵遑ｭ｣ｿ`（其中 `｡ｭ｣ｿ` 在游戏字体下渲染即为 `。ュ...ュ」ソ`）。
  - `crates/wolf-format/src/bytes.rs:312-320`：
    ```rust
    if !cp_bad && !gb_bad && cp_looks_japanese(&cp) && has_halfwidth_kana(&cp)
        && cp932_kanji_pairs(raw) >= 1 && gbk_kanji_lead_pairs(raw) >= 1
    {
        return (cp, cp_total);
    }
    ```
- **根因分析**：这段为修复汉化边界而加的启发式规则原本用于保护含半角片假名的日文字符串不被误判为 GBK；但当中文 GBK 文本同时包含 `…`（`A1 AD` -> CP932 半角 `｡ｭ`）、`？`（`A3 BF` -> CP932 半角 `｣ｿ`）以及某些双字节汉字（如 `哥` `B8 E3`、`为` `CE AA`）时，恰好同时满足了 `cp_looks_japanese`、`has_halfwidth_kana`、`cp932_kanji_pairs >= 1` 和 `gbk_kanji_lead_pairs >= 1`，从而被**强制走入 CP932 分支**，产生乱码。
- **修复建议**：收紧 `bytes.rs:312-320` 的兜底条件，不能仅凭出现半角标点符号映射（`A1..AF` 区段的 `｡｢｣､･ｦｧｨｩｪｫｬｭｮｯ`）就判定为「日文真实半角片假名」；应排除 `A1..DF` 中对应 GBK 全角标点（`A1 AD` `…`、`A3 BF` `？`、`A1 A3` `。` 等）造成的伪半角假名，并优先结合正常 GB2312 高频区（`B0..F7`）占比打分。

### 7. 转场黑屏时顶部状态栏正常但行动力条消失

- **问题现象**：在黑屏转场期间顶部状态栏已正常显示，但「行动力」文字右侧的进度条空白消失，只剩 `行动力   50/75 精力 3/3`（见 `{CAEE364F-A9A0-4F55-803B-1D7109F1D22C}.png`）。
- **代码定位**：
  - `crates/wolf-game/src/game.rs:2073-2078`：在 `hud_action_points()` 中，若检测到 `self.screen.get(-1)` 或 `self.screen.get(9000)` 满足 `!hidden && opacity > 0`，则直接返回 `None`。
  - `crates/wolf-game/src/game.rs:1770-1772`：`if self.hud_action_points().is_none() { quads.retain(|quad| quad.number != HUD_ACTION_PICTURE); }` 直接把行动力条剔除。
- **根因分析**：这是此前为修复「全黑屏时仍显示孤立行动力条」而加的过度保护。游戏实际在日常黑屏转场中使用的 `Picture -1` 位置是 `y = 36`（`150 [1, -1, 30, 0, 0, 1, 255, 0, 36, 100, 0]`），**并不覆盖 `y = 0..36` 的顶部状态栏**。只要 `slot -1` 存在且不透明就一刀切返回 `None`，导致所有使用 `slot -1` 遮罩下方画面的转场里，顶部行动力条都被错误隐藏。
- **修复建议**：移除 `hud_action_points()` 中对 `slot -1`（`y >= 36`）的屏蔽条件；仅当真正的全屏遮罩（覆盖 `y < 36` 的顶部状态栏区域）或 `CE 242` 尚未写出有效 `行动力 current/max` 文本时，才隐藏行动力条。

### 8. 黑屏转场没有渐变过渡（直接瞬黑再切换）

- **问题现象**：原版黑屏转场是背景在较短时间内逐渐变黑、切换场景后再在较短时间内渐变亮；当前版本则是画面直接瞬间变黑，然后直接切到下一个场景。
- **字节码与代码定位**：
  - 字节码实测：`_ce_full.json` 中全作未在普通转场使用 `Opcode 151/161/162`；`CE 249`、`CE 251`、`CE 256` 等全部通过 `Picture -1` 实现黑幕转场：
    - 渐黑：`150 [1, -1, 30, 0, 0, 1, 255, 0, 36, 100, 0]`（`PictureAction::Move`，目标 `opacity = 255`，`fade = 30` 帧）
    - 渐亮：`150 [1, -1, 30, 0, 0, 1, 0, 0, 36, 100, 0]`（`PictureAction::Move`，目标 `opacity = 0`，`fade = 30` 帧）
  - `crates/wolf-game/src/picture.rs:1284-1331`：`PictureAction::Move` 在槽位 `-1` 尚未存在时调用 `Picture::new(num)`。
- **根因分析**：`Picture::new(num)` 默认将初始 `opacity` 设为 `255`。当脚本首次对不存在的 `Picture -1` 执行 `150 Move (opacity=255, fade=30)` 企图从透明渐变到全黑时，`origin.opacity` 是 `255`，`target.opacity` 也是 `255`，`Transition::from_command` 计算出的透明度插值就是 `255 -> 255`，导致**第一帧直接全黑（0 帧瞬黑）**；部分脚本在黑屏前并未先 `Show` 一个 `opacity = 0` 的 `-1` 槽位，从而使所有首次渐黑转场全部失去渐变效果。
- **修复建议**：核实 `PictureAction::Move` 命中尚未创建的槽位时（或针对未初始化先 `Move` 淡入的槽位），其隐式初始 `opacity` 应按 `0` 处理（而非 `255`），使 `0 -> 255` 能够按 `fade=30` 帧正常执行渐黑插值；同时确认渐亮阶段 `255 -> 0` 的 `Transition` 不被后续同名 `Show` 提前覆盖。

### 9. 晚上卧室侧拉栏收起时直接消失（无拉回动效）

- **问题现象**：晚上卧室界面展开左侧状态栏或物品栏后，鼠标移开或点击收起时，侧拉栏直接从画面上消失，没有原版向左平滑缩回的动效。
- **字节码与代码定位**：
  - `CE 238`（`ステータス`）与 `CE 239`（`アイテムリスト`）：
    - `pc=2` 判断 `arg0 == 0`（隐藏）还是 `arg0 == 1`（显示）。
    - **隐藏分支（`pc=4..5`）**：`pc=5` 执行 `150 [0, 320, 10, 1, 1, 1, 255, 1600020, 0, 100, 0]`，注意头字是 `0`（**`PictureAction::Show` 瞬间定位**），直接将 `Picture 320`（或 `2300`）瞬移到 `x = -305`！
    - **显示分支（`pc=68..69`）**：`pc=69` 执行 `150 [65536, 320, 20, 1, 1, 1, 255, 1600010, 0, 100, 0]`，才是相对移动滑出。
  - `crates/wolf-game/src/game.rs:2948-2982, 3038-3112`：`tick_side_panel_auto_retract()` 与手柄点击逻辑直接调用 `self.start_panel_event(238, 0)` / `self.start_panel_event(239, 0)`。
- **根因分析**：`CE 238/239` 的 `arg0 == 0` 分支在脚本里原本就是无动画瞬移重置到 `x = -305`（而原版实际平滑收起是由地图事件 8/11 的 `150 Move` 驱动）。宿主侧的 `tick_side_panel_auto_retract()` 和点击收起逻辑为了避免 `hover` 问题直接调用了 `CE 238/239(0)`，于是就触发了 `pc=5` 的无动画瞬移，导致侧拉栏直接消失。
- **修复建议**：收起侧拉栏时不要直接调用瞬移的 `CE 238/239(0)` 覆盖位置，应改用带时长（如 `5~8` 帧）的 `150 Move` 将 `320`/`2300` 及附属文字槽位平滑滑回 `x = -305`（或由宿主触发原版对应的平滑收起事件路径）。

## 三、本地核实确认保留项（E 项与 F 项）

### E 项：本地时钟语义与 `m14` 确定性测试基线

- **位置**：`crates/wolf-game/src/game.rs:353-394, 3682-3688`
- **现状与影响**：`current_datetime()` 当前读取系统 UTC 时间而非本地时区时间。虽然 `Sys80`（小时）无脚本读取，但 `Sys79`（日）在本地时间 `00:00–08:00`（UTC+8）期间会比本地日期慢一天，影响该时段内 `CE 251 / 256 / 257 / 258` 及地图 `ev24` 的日期判定；同时 `m14` 基线测试因未钉住时钟而在不同环境/时段下出现 `7 vs 8` 的漂移。
- **修复方案**：
  1. 运行期对齐零售版 `GetLocalTime`，读取系统本地时间；
  2. 为 `Game` / `Vm` 提供可注入或可冻结的测试时钟接口，在 `m14` 等确定性回归测试中固定测试时间戳并重新锁定基线。

### F 项：读档后地图路径缺失 `.mps` 后缀

- **位置**：`crates/wolf-game/src/game.rs:2798`
- **现状与影响**：`resume_loaded_map()` 将 `current_map_path` 设为 `Some(format!("MapData/{name}"))`，遗漏了 `.mps` 扩展名，导致读档恢复后 `db.rs:255` 的 `map_scenery_by_path` 查找失败，无法匹配并显示对应地图的背景图（`scenery_quad -20_000`）。
- **修复方案**：在 `resume_loaded_map()` 中将路径格式修正为 `Some(format!("MapData/{name}.mps"))`（若 `name` 尚未包含 `.mps`），并在读档回归测试中校验背景图四元组正常输出。
